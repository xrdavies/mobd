# 客户端添加、配对和撤销（设计，尚未实现）

桌面和手机使用同一份添加链接，二维码只是这份链接的另一种表达。
办公室 mobd 根据服务端认证设置生成链接：启用认证时附带短期邀请，关闭认证时只包含连接信息。
**邀请过期只影响新增配对，不影响已经配对的客户端。**

本文确定行为和最小实现边界，不代表当前 mobd 已支持以下命令或接口。
网络通道见 [remote access](remote-access.md)，当前认证边界见 [security](security.md)。

## 三种不同的有效期

| 对象 | 建议有效期 | 用途和失效结果 |
| --- | --- | --- |
| 普通添加链接/二维码 | 不主动过期；地址或服务器身份变化后需更新 | 保存办公室地址和名称，不授予权限；重复添加同一机器应去重 |
| 配对邀请链接/二维码 | 第一版固定 10 分钟、单次兑换，也可提前作废 | 仅用于领取一个客户端的凭据；过期后不能再新增配对 |
| 已配对客户端凭据 | 第一版长期有效，直到撤销、删除或重置认证数据 | 自动认证、重连；与邀请有效期无关，不随 mobd/客户端重启失效 |

10 分钟是产品建议值，不是协议要求。邀请使用加密随机数，不能由时间或设备名推导。
一个邀请只配对一个客户端；桌面和手机分别领取邀请，不共用长期凭据。
未使用的邀请过期后在办公室重新生成。第一版不需要建立账号系统或 refresh-token 服务。
如以后增加客户端凭据有效期，应另设生命周期，不能把邀请的过期时间用作客户端失效时间。

## 启用认证时

1. 办公室用户通过本地管理命令生成邀请，指定客户端可访问的 URL；mobd 不能从
   `127.0.0.1:8080` 推断私有域名、Funnel 地址或我们的中继地址。
   输出同一邀请的链接、二维码及过期时间。
2. 桌面客户端打开/粘贴链接；手机客户端扫描二维码或打开链接。客户端展示目标办公室，
   用户确认添加后，向该入口提交邀请进行兑换。单纯预览或 HTTP GET 不得消耗邀请，
   避免聊天软件的链接预览提前使用它。
3. mobd 校验邀请仍有效，原子地消费邀请并登记客户端，签发独立的随机凭据。
   并发兑换最多成功一次。客户端凭据记录持久化成功后才能返回成功；失败不能退回匿名访问。
   如果响应丢失且客户端未保存凭据，显示重新获取邀请，不能为了重试重新开放已消费的邀请。
4. 客户端保存地址、办公室身份、客户端 ID 和凭据。后续启动、网络切换、断线重连
   都使用保存的凭据，不再使用或保存邀请 secret。
5. mobd 校验每个受保护请求的凭据及客户端状态，并跟踪它的 SSE/VNC 连接以支持撤销。

邀请在有效期内相当于一次授权，拿到邀请的人可以领取访问权，因此不生成永久的可兑换邀请。
链接只携带短期邀请，**不能携带长期客户端凭据或 `sharedSecret`**。
应用链接格式需在 mob 仓库共同确定；邀请 secret 应避免出现在普通 HTTP 查询参数、
访问日志、分析事件或中转页面请求中，例如由客户端读取 URI fragment 后通过 HTTPS POST 兑换。
fragment 不能防止链接本身被复制或被接收应用读取，仍需单次使用和过期。
客户端不得跳过证书验证，不跟随跨来源重定向发送邀请或凭据。

二维码和完整链接可携带足够长的随机邀请，不必另外设计短数字码。
如后续支持手输短码，需要服务端限速和尝试次数限制。
短码过期与防猜测参考 [RFC 8628 §5.1](https://www.rfc-editor.org/rfc/rfc8628.html#section-5.1)，
这里只复用安全原则，不声称实现 OAuth Device Grant。
长期 bearer 凭据避免放在 URL，参考 [RFC 6750 §2.3](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.3)。

## 双方如何保存配对信息

| 保存方 | 保存内容 |
| --- | --- |
| mob 客户端 | 办公室身份、地址、客户端 ID；随机凭据放系统安全存储 |
| mobd | 稳定的办公室身份；客户端 ID、名称、凭据哈希、创建时间、最后认证活动时间、撤销状态 |
| mobd 运行内存 | 当前请求/SSE/VNC 与客户端 ID 的关联；未兑换的短期邀请可仅保存在内存中 |

mobd 不需要保存可直接使用的客户端 token 明文；随机 token 的哈希用于校验。
认证数据保存在私有文件中并原子更新，重启后读取；记录缺失或损坏时不能自动关闭认证。
每次请求由服务端查询记录，未知、已撤销、已删除的客户端都拒绝访问。
第一版使用可查表撤销的随机凭据，不需要额外引入 JWT。
存储原则参考 [OWASP 会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#server-side-session-token-storage)。

例如 10:00 生成邀请、10:03 手机完成配对，10:10 邀请过期。第二天手机依然使用自己的
凭据连接，不需要再次扫码；另一个电脑在 10:10 后打开旧链接则只能保存办公室信息，
必须获取新邀请才能访问受保护资源。

清空客户端安全存储或重置 mobd 认证数据需要重新配对。重置前应使旧入口和连接失效。
恢复旧认证备份可能恢复曾撤销的授权，不能用旧备份覆盖当前撤销状态。
服务器地址变化不会自动使配对失效，但更换入口前必须确认它属于原办公室，不能把
旧凭据直接发送给链接指定的新地址。服务端 ID 是查找标识，本身不是服务器身份的密码学证明。

## 关闭认证时

链接仅包含地址、显示名称和用于去重的办公室标识，不包含邀请或凭据，可以长期保存。
客户端添加后直接使用服务。服务端设置是最终依据，链接声称“不需要认证”不能绕过
已经启用认证的 mobd；客户端此时应显示需要配对。

**没有认证就没有可可靠撤销的客户端身份。** mobd 可显示当前连接、最近活动和客户端
自报名称，但这些都是观测信息；代理后的 IP 可能相同，自报 ID 或名称也可伪造。
断开连接后对方仍可重连，删除一条观测记录不能禁止它再次访问。要使用持久的按客户端
`revoke`，必须开启认证。无认证模式只面向明确受信任的私有网络，不用于直接公开的 Funnel。

关闭认证与“停止接受新配对”必须分开：后者只作废未使用邀请，不解除现有访问检查。
重新开启认证后，旧的匿名添加记录不能自动获得授权；已有且未撤销的配对仍可使用。
关闭认证期间撤销不能阻止匿名访问，但记录的撤销状态必须保留，重新开启后仍拒绝该凭据。
切换认证设置需要同步处理已有匿名连接，不能只影响下一次连接。

## 本地管理命令（建议接口，尚未实现）

| 建议命令 | 行为 |
| --- | --- |
| `mobd link --url https://office.example.com` | 根据当前认证设置输出二维码和链接：启用认证则创建邀请，否则只输出连接信息 |
| `mobd clients list` | 列出已配对客户端，包括离线、已撤销设备；显示创建时间和最近认证活动 |
| `mobd connections` | 列出当前活跃请求/长连接，关联已认证客户端；匿名连接明确标识为匿名 |
| `mobd clients revoke CLIENT_ID` | 使凭据失效、断开该客户端 SSE/VNC 等连接，保留已撤销记录 |
| `mobd clients delete CLIENT_ID` | 先完成撤销和断连，再删除配对记录；旧凭据仍因查不到记录而被拒绝 |

客户端名称只是方便识别的标签，授权以凭据为准。HTTP 请求可能很短，不能把“已配对”
等同于“当前在线”；没有活跃连接也不代表没有配对。第一版用“最后活动”和“活跃连接数”，
不为展示在线状态另加心跳协议。

撤销不回滚已经完成的动作，也不自动取消此客户端提交的 agent 任务；任务取消使用已有任务 API。
客户端收到认证失效后保留办公室列表项、标记需重新配对，不反复重试旧凭据。
删除配对不删除办公室会话和任务，客户端也不能用自报的旧 ID 自动重新登记。

管理入口限办公室本机用户。建议使用受操作系统权限保护的本地 IPC，由运行中的 mobd
统一修改状态并即时断连，避免 CLI 离线改文件后守护进程仍接受旧凭据。
不能仅凭 HTTP 请求来自 `127.0.0.1` 授权管理操作：Serve/Funnel 转发也会来自本机。

## 实施范围与验收

mobd 需要认证设置、邀请兑换、客户端记录持久化、完整接口认证、连接关联和上述 CLI；
mob 需要桌面链接处理、手机扫码/链接处理、安全存储及失效提示。配对与网络模式无关，
三种连接方式共用这些能力。公网使用 HTTPS，CORS 和 VNC 来源校验继续保留。
本地 agent/MCP 的按任务认证保持独立，不能为了公网配对破坏它。

实施时最少验证：邀请过期及重复/并发兑换；邀请过期后旧客户端仍可访问；重启保存配对和撤销；
撤销一个客户端不影响其他客户端；revoke/delete 同时阻止新请求并断开旧 SSE/VNC；匿名记录不能用于永久封禁；
启用认证后匿名连接失效；链接预览不消耗邀请；持久化失败不签发可用凭据。
WebView 的 SSE/图片/WebSocket 凭据传递要在真实客户端验证；必要时通过已认证请求
获取短期、单次、限用途的连接票据，不把长期凭据塞进 URL。
